Software Manual

The SCCo Packet Messenger software supports Amateur Radio Emergency Service (ARES®) packet radio messaging in Santa Clara County, California. It is the successor to PacFORMS (by Phil Henderson KF6ZFQ), PackItForms (by John Kristian W6JMK), and packet shell (by Steve Roth KC6RSC). The Packet Messenger software operates in two modes: as an Outpost add-on, and as standalone packet messaging software.

Most Santa Clara County ARES/RACES packet operations and operators use the Outpost Packet logentry Manager software, which is the county standard packet message manager. In these environments, the SCCo Packet Messenger acts as an add-on to Outpost, adding the ability to send and retrieve messages containing standard county forms.

The SCCo Packet Messenger can also be used as a packet message manager in its own right, independent of Outpost. It provides both a graphical user interface and a scriptable command line interface. It supports both manual operation (operator interacts with TNC) and automatic operation (software handles the TNC). It runs on any operating system and has no external dependencies other than a browser for the graphical user interface.

Outpost Add-On Operation

The SCCo Packet Messenger software is bundled in the county standard packet software installer. When installed using that installer, it is automatically connected to Outpost. If the SCCo Packet Messenger software is installed separately for some reason, it can be connected to Outpost by running the packet install command. The connection can be broken with the packet uninstall command, or by uninstalling the SCCo Packet Messenger software.

Whenever an Outpost user asks to view a forms message (i.e., one that starts with !SCCoPIFO! or similar), Outpost will relay the request to the SCCo Packet Messenger, which will render the original form in PDF format and open it in a browser window.

Similarly, whenever an Outpost user asks to create a new forms message using one of the entries in the "Forms" menu, Outpost will relay the request to the SCCo Packet Messenger, which will open the appropriate form in a browser window. When the user submits that form, the SCCo Packet Messenger will encode it for transmission and hand it back to Outpost. It will also render the message in PDF format so that it can be printed if desired.

The first time that the SCCo Packet Messenger is used each day, it will contact the SCCo ARES/RACES web server and look for updated versions of the Santa Clara County standard forms. These will be installed automatically. (Obviously this only works if the system has Internet access.)

The SCCo Packet Messenger software handles all county standard forms. Individual systems may have other Outpost add-ons that handle other forms, such as city-specific forms. These are independent and not affected by the SCCo Packet Messenger.

Standalone Packet Messenger Operation

The SCCo Packet Messenger can be used without Outpost, in both graphical and command line interfaces. When run standalone, it operates on an "incident", which is a folder containing a set of related messages that get reported on the same ICS-309 message log form. A new "incident" should be created in a new folder whenever you would normally start a new ICS-309.

Graphical Interface

To start the SCCo Packet Messenger's graphical interface, run the packet gui command (or, if installed on Windows through the SCCo standard packet installer, C:\PackItForms\pifo.exe, which is usually installed as the "SCCo Packet" desktop shortcut). The graphical interface runs in your system's default browser. Only recent, modern browsers are supported.

If you are in an incident folder when you start the graphical interface, or you add a folder path on the command line, the graphical interface will start in that incident. Otherwise, it will ask you to choose or create an incident folder. In the graphical interface, use the Incident → New Incident or Incident → Open Other Incident menu items to change which incident you are working on.

The grahical interface maintains no state information in your browser. You may close your browser at any time and start the graphical interface again at a later time to resume where you left off. (However, if you are editing a message in a browser window, any unsaved changes to the message will be lost when you close it.)

Command Line Interface

The SCCo Packet Messenger's command line interface is available through the packet command. If you invoke the packet executable with a command on the command line, it will execute that single command and stop. If you invoke it without any arguments, it will open a shell in which you can issue multiple packet commands. The shell continues until you run the quit command.

Packet commands are fully spelled out in this manual, but any unambiguous abbreviation of them is accepted (e.g., q for quit). To get help on any command, use the help command.

Some packet commands produce different output in "scripted mode", which is when standard input or standard output are not connected to a terminal (e.g., output is redirected to a file). Specific differences are noted in the command descriptions below. Generally, in scripted mode:

  • Confirmation and transient status messages are suppressed.
  • All colorization of the output is suppressed.
  • Commands that normally produce tables will produce CSV output.
  • Error messages are written to standard error instead of standard output.

Packet commands operate on the incident folder that is the current working directory when they are run. To move between, create, and query incident folders, use the chdir (or cd), mkdir, and pwd commands, either in your command shell before invoking packet or from within the packet shell.

Many packet commands take a «message» argument identifying a message in the incident. This can be the full local message ID of the message (e.g., AAA-111P), the full remote message ID of the message if it is unambiguous (e.g., XND-2345P), the sequence number part of either message ID if it is unambiguous (e.g., 111), or a number sign followed by the log entry number for a log entry describing the message (e.g., #23).

Incident Settings

Each incident has its own settings that control how its messages are handled. Only a few of the settings are required:

  • Your call sign and name. You can also supply a tactical call sign and station name if appropriate.
  • The starting message ID to be assigned to new messages. You can assign separate message ID sequences for incoming and outgoing messages, but usually they share the same sequence. (The software will guess a likely message ID sequence based on your call sign or the tactical call sign, but you can override this.)
  • The BBS you're connecting to and the method of connecting to it. Three connection methods are currently supported:
    • Manual operations. The SCCo Packet Messenger doesn't connect to the BBS for you; it just gives you commands you can paste into a separate connection that you manage. For this method, you need to provide the BBS name (so the software can use it in message headers). You can also decide whether the software should automatically generate delivery receipts for received messages (which you would then need to send manually).
    • Serial+TNC connection. The SCCo Packet Messenger will connect to the BBS (that you specify by AX.25 address) by talking to a TNC (of a type you specify) through a serial port (that you specify).
    • Telnet connection. The SCCo Packet Messenger will connect to the BBS (that you specify by name, hostname or IP address, and port number), logging in with your tactical or FCC call sign and the password you specify. (Note: SCCo ARES/RACES issues passwords for telnet access only to network maintenance staff and others with demonstrated need.)

The rest of the incident settings are optional. These include:

  • ICS-309 header information: incident name, activation number, and operational period. These are shown on the generated ICS-309 forms.
  • Bulletin retrieval settings: you can specify which BBS areas to retrieve bulletins (and SCCo notices) from, and how often to check for them. (These settings are not available for manual operations.)
  • Defaults for new messages: you can specify default values for the To Address, To ICS Position, To Location, From ICS Position, and From Location fields of messages. You can also specify default body text (e.g., **** This is drill traffic ****) to be put in the primary text field of new messages.

When creating a new incident it the graphical interface, you are prompted to supply these incident settings (at minimum the required ones). To change them later, use the Incident → Incident Settings menu item (graphical interface). In the command line interface, you supply incident settings with the edit config or set config commands. In interactive mode, you will be prompted for the required ones if you have not set them prior to an operation that needs them. (In batch mode, you'll get an error.)

Incident Log

An incident consists of a set of ICS-309 log entries. Most of the time, there is one entry per packet message. However, packet messages sent to multiple recipients will have a log entry per recipient. Also, log entries can be added manually that do not correspond to any packet message, such as shift change notations.

The log can be formatted in either of two layouts. When rendered as an PDF ICS-309 form, it uses the traditional 6-column layout of the SCCo-standard printed ICS-309 form. When rendered on screen in the command line interface, it uses a more compact layout with 5 columns, described below. When rendered on screen in the graphical interface, you can choose either layout using the View → Compact menu item toggle.

The compact layout has the following columns:

  • The "TIME" column contains the time of day of the log entry. (ICS-309 logs should never span more than 24 hours, so the column does not display the date.)
  • For messages that the local station has received, the "FROM" column indicates the origin of the message: either its origin message ID, if known, or its origin station call sign. (For bulletins, it shows the BBS area that the bulletin was retrieved from.)
  • The "MSG ID" column displays the local message ID of the message. For receipt messages, it displays the local message ID of the message described by the receipt.
  • For messages that the local station has sent, the "TO" column indicates one destination of the message: either its destination message ID, if we've received a receipt for it giving that information, or else the destination station call sign. (If the local station sends a message to multiple recipients, there will be a separate log entry for each.)
  • The "MESSAGE" column contains the subject line of the message. (In the compact layout, if the subject line starts with a message ID that is displayed in another column, the message ID is omitted here to save space.)

Note: the above descriptions indicate what the software puts in each column when creating, sending, or receiving a packet message. The descriptions may not hold if the user manually adds or edits log entries.

The colors of the log entries indicate the message severity. Immediate messages are shown in red; priority messages are shown in gold. Bulletin messages are shown in blue. Log entries for receipt messages are normally not shown, but when they are requested, they are shown in gray.

Log entries may be decorated with a number of markers. These appear only on screen, not in the generated ICS-309 PDF form.

  • A DRAFT marker in the "TIME" column indicates that the message is being written and is not yet ready to send.
  • A READY marker in the "TIME" column indicates that the message will be sent the next time the software connects to the BBS, but that it has not been sent yet.
  • A NO RCPT marker indicates that we have not yet received a delivery receipt for the message (which we sent). This marker appears in the "TO Msg #" column in the traditional layout and the "FROM" column in the compact layout.
  • A NEW marker in the "MESSAGE" column indicates that the message (which we received) has not been read yet.
  • A red star (★) in the right margin indicates that the message needs follow up.

Delivery receipts (other than unsent ones) are normally not shown in the on-screen log (although they are always included in the printed log). To show receipts in the on-screen log, use the View –> Receipts menu item toggle in the graphical interface, or the --receipts (or -r) flag on the list command in the command line interface.

To generate the ICS-309 in PDF format, use the Incident → Generate ICS-309 menu item in the graphical interface, or the ics309 command in the command line interface. The PDF will be created in the file "ics309.pdf" in the incident folder, and will be shown in the system default PDF viewer.

Sending Messages

To create a draft of an outgoing message:

  • Graphical Interface: Use the Message → New menu item (or the "N" key), and then choose the message type by clicking on it or typing the letter(s) next to it. This will open a new browser window for the message.
  • Command Line Interface, Interactive Mode: issue the new «type» command, where «type» is the tag or abbreviation of the message type. (Use the forms list command to get the tags and abbreviations of the available types.) You will be put into the command line editor for the new message.
  • Command Line Interface, Scripted Mode: use the new command as above, but no command line editor will start. Instead, the local message ID of the new message will be printed to standard output. You can then use that in subsequent set commands to set the fields of the new message. To override the default assignment of the new message ID, add your desired message ID on the new command line after the message type.

To revise an existing draft message:

  • Graphical Interface: To open a new browser window to edit a message:
    • Double-click on its log entry in the incident window,
    • Select its log entry and press Enter,
    • Right-click its log entry and select Edit in the context menu, or
    • Select its log entry and use the Message → Edit menu item
  • Command Line Interface: use the edit «message» command to start an interactive editor on the message, or the set «message» «field» «value» command to set an individual field's value.

To mark a draft message as being ready to send during the next BBS connection:

  • Graphical Interface:
    • Click the "Send Message" button at the top of the message form. (Only available if all message fields are valid.)
    • Right-click its log entry and turn on the Ready to Send item in the context menu.
    • Select its log entry and turn on the Ready to Send item in the Message menu.
    For the latter two methods, if the message contents are not valid, you will be prompted to confirm that you want to send it anyway.
  • Command Line Interface: At the completion of interactive editing, if all fields are valid, you will be asked whether it is ready to send, and you can select Yes. In other cases, use the mark «message» ready command. You will have to add a --force flag if the message contents are not valid.

To mark a draft message as not ready to send:

  • Graphical Interface:
    • Click the "Save as Draft" button at the top of the message form.
    • Right-click its log entry and turn off the Ready to Send item in the context menu.
    • Select its log entry and turn off the Ready to Send item in the Message menu.
  • Command Line Interface: At the completion of interactive editing, if all fields are valid, you will be asked whether it is ready to send, and you can select No. In other cases, use the mark «message» draft command.

To delete a draft message without sending it:

  • Graphical Interface: Select its log entry and use the Delete menu item in the Message menu or the right-click context menu.
  • Command Line Interface: Use the delete «message» command. Note that this command does not accept abbreviations of the message ID, for safety. Only the full message ID or the #NN log entry identifier are accepted.

To display the JNOS command needed to send a message manually:

  • Graphical Interface (when connection type is Manual): Select its log entry and press "S" or use the Manual Send menu item in the Message or right-click menu. The resulting dialog will show you the send command, and has a button to copy it to your system clipboard so that you can paste it into a terminal emulator. When finished, use the Mark Message as Sent button to tell the packet software that the message has been sent.
  • Command Line Interface: Use the manual send «message» command to display the send command. In interactive mode, it will ask you to confirm that the message has been sent. In batch mode, use the mark «message» sent command to mark the message as sent.

To resend a message (i.e., edit a message that has already been sent and send it again, with the same message number except with an "R" suffix):

  • Graphical Interface: Select the log entry of the sent message and use the Resend menu item in the Message or right-click menu. This will open a new browser window to edit the new draft message.
  • Command Line Interface: Use the new --resend «message» command.

To send a copy of a message (i.e., send a message with an entirely new message number but the same contents as an existing message):

  • Graphical Interface: Select the log entry of the message to copy and use the Send Copy menu item in the Message or right-click menu. This will open a new browser window to edit the new draft message.
  • Command Line Interface: Use the new --copy «message» command.

To reply to a received message (i.e., send a new message to the sender of the received message, with the same subject):

  • Graphical Interface: Select the log entry of the message to copy and use the Reply menu item in the Message or right-click menu. This will open a new browser window to edit the new draft message.
  • Command Line Interface: Use the new --reply «message» command.

Delivery receipts for received messages are generated automatically, unless the incident connection type is Manual and the option for automatic delivery receipts has been turned off. In that case, you can generate a draft delivery receipt manually:

  • Graphical Interface: Select the log entry of the received message and use the Create Receipt menu item in the Message or right-click menu.
  • Command Line Interface: Use the manual make-receipt «message» command.

Receiving Messages

To connect to the BBS and receive messages (for "Serial+TNC" and "Telnet" connection types):

  • Graphical Interface: Press "C" or use the Connect → Send/Receive All menu item. (To transfer immediate messages only, use the Connect → Immediates Only menu item.)
  • Command Line Interface: Run the connect command. (To transfer immediate messages only, add the --immediates flag.)

To receive a message manually (for "Manual" connection type):

  • Graphical Interface: Press "R" or use the Message → Manual Receive menu item to bring up the Manual Receive dialog. Paste the received message into the box, or use the button to upload a file containing it.
  • Command Line Interface: Run the manual receive command and paste the received message. End it by typing /EX on a line by itself. Alternatively, use manual receive < «filename» to read the received message from a file.

Other Message Operations

To view a message (sent or received):

  • Graphical Interface: Double click on the message, select it and hit return, select it and use the Message → View menu item, or right-click on it and use the View menu item in the context menu. The message will be shown in PDF format in a new browser tab.
  • Command Line Interface: Use the show «message» command to display the message contents in the console window, or the pdf «message» command to display the message in PDF format in the system default PDF viewer.

To send a message to the system default printer:

  • Graphical Interface: Select the message and press "P", or use the Print menu item in the Message menu or the right-click menu.
  • Command Line Interface: Use the print «message» command.

Log Entry Operations

The software automatically creates one log entry for each received message, and one for each recipient of each sent message. You can edit these, and create additional log entries not associated with a sent or received message.

To create a log entry not associated with a packet message:

  • Graphical Interface: Use the Message → Manual Log Entry menu item. This will give a dialog box for entering the log entry details.
  • Command Line Interface: Use the new logentry command. This works the same way as the new command for a message, giving you a console editor for the new log message in an interactive session or printing the new log entry number to standard output in scripting mode.

To edit a log entry:

  • Graphical Interface: Select the entry and use the Edit Log Entry menu item in the Message menu or the right-click content menu. This will give a dialog box for changing the log entry details.
  • Command Line Interface: Use the edit log «logentry» command for an interactive editor of the log entry, or the set log «logentry» command to change individual log entry fields.

To delete a manually added log entry (or a draft message):

  • Graphical Interface: Select the entry and use the Delete menu item in the Message menu or the right-click content menu.
  • Command Line Interface: Use the delete «logentry» command.

The software automatically flags log entries for sent messages for which no delivery receipt has been received. To clear this flag (e.g., because you know the message has been received through some other means):

  • Graphical Interface: Select the log entry and turn off the Needs Receipt menu item toggle in the Message menu or right-click context menu.
  • Command Line Interface: Use the mark «logentry» received command.

To change whether a log entry is marked as needing follow-up:

  • Graphical Interface: Select the log entry and toggle the Needs Followupt menu item toggle in the Message menu or right-click context menu.
  • Command Line Interface: Use the mark «logentry» starred or mark «logentry» unstarred command.

Reporting Issues

Issues with this software should be reported to the packet@scc-ares-races.groups.io mailing list. When reporting problems, please include the relevant files:

  • The log file(s) for the day(s) when the issue occurred. Log files are located in C:\PackItForms\Log on Windows and in $HOME/.local/state/packet/log on other operating systems.
  • If the issue is with standalone operation, include the incident configuration file, which is packet.json in the incident folder.
  • If the issue is with BBS communications, include the BBS communication transcript, which is «BBSname».log in the incident folder.

Folders and Files

This section describes where folders and files are located and how data is stored. It is for background only; this information is not needed to use the software.

Incident Folders

Incident folders can be located wherever the user decides to create them, although the software will block usage of some unsuitable directories. Within an incident folder, there are four incident-related files:

  • packet.json contains the incident configuration, log entries, and other associated data.
  • .packet.lock is a lock file ensuring synchronized access to incident data.
  • ics309.pdf and ics309.csv contain the rendered ICS-309 log for the incident.

In addition, there are two files for each message: a .txt file with the message in encoded form, and a .pdf file with the message in PDF format. For sent and received messages other than receipts, the filename is the local message ID. For receipts, the filename is .receiptNN, where NN is the corresponding log entry number. For unsent messages, the filename is .unsentNN.

Where the remote message ID of a sent or received message is known, it may be available under that filename as well. (On Windows, this only works if user symbolic link permissions have been enabled, which is not common.)

Finally, if the incident has connected to a BBS, there will be a «BBSname».log file containing the transcript of the communications.

System Files

Outside of the incident folders, the packet software stores a number of other files:

  • Form definitions and related files are stored in C:\PackItForms\Forms on Windows, and in $HOME/.local/share/packet on other operating systems.
  • Log files are stored in C:\PackItForms\Log on Windows, and in $HOME/.local/state/packet/log on other operating systems.
  • Messages transferred between Outpost and the packet software are stored in C:\PackItForms\Spool.
  • Settings that persist across all incidents are stored in %APPDATA%\packet.json on Windows, and in $HOME/.config/packet/packet.json on other operating systems.
